# Pixel Docs (static lab port)

A static port of the documentation site that lived in `packages/pixel/src/docs`. The page keeps the
same information architecture — overview, one view per manipulation, resize/chaining pipeline pages
and six internals pages — but renders it with plain HTML and native DOM controls. Every interactive
demo runs through the same off-thread engine as the Pixel Manipulator page.

## What was ported

- The documentation copy is now static markup in `index.html`: overview, pipeline and internals text
  is written once and is never rebuilt by JavaScript.
- The manipulation catalog is read from the shared engine (`getManipulations()`), so the sidebar,
  badges, descriptions, parameter table, slider ranges, defaults and generated code sample stay in
  sync with the 18 registered manipulations. The `manip` view is a single section populated from
  metadata when a sidebar entry is selected.
- `Try It Out` recreates the original experiment: moving a slider re-runs one step on the sample
  image and shows the new snapshot and its dimensions.
- `Resize` runs five variants (width, height, fill, contain, cover) and reports the resulting size.
- `Chaining` runs brightness → contrast → sharpen and shows one figure per snapshot, including the
  source.
- The status line and error box use the shared lab styles; a generation counter discards late worker
  replies when the user switches views or changes a control quickly.

## Shared engine

The DOM-free engine was extracted once into `apps/lab/lib/pixel-core/` during Session 7 and is used
by both `pixel` and `pixel-manipulator`:

- `processor/**` — `processImage()`, the manifest-derived `Step` union, buffer manager, fusion
  scheduler, step dispatcher, neighborhood tiling and all manipulations.
- `worker/pipeline-worker.ts` — the module worker entry point.
- `worker/serialization.ts` — response validation.
- `worker/process-image-in-worker.ts` — catalog helpers and `createPixelPool()`.

`createPixelPool()` creates the worker with Vite's `new URL(..., import.meta.url)` pattern next to
the bridge, so both pages emit a correctly hashed worker chunk. The pool uses the shared
`lib/worker-pool/` with `maxPoolSize: 1`: replies stay in request order and the generation counter
handles staleness. `teardown()` runs on `pagehide`.

## Porting choices

- The former documentation state store and React selectors became four small module values in
  `main.ts`: the active endpoint, the selected manipulation, the resize mode and the run generation.
- Sidebar groups are built once with `buildNavigation()`. Each view is a static section with a
  `data-view` key; `selectView()` only toggles `hidden` and `aria-current`. No route, no hash and no
  history entry are involved.
- Sliders come from `ui/controls.ts`; the shell, panel and theme come from `ui/shell.ts`,
  `ui/theme.ts` and the shared `ui/styles/` files. Group headers are collapsible via `aria-expanded`.
- The sample source is generated by `createSampleImageData()` from `ui/image-data.ts`, a 200 px
  gradient with colored shapes. The original `geant.jpg` asset is not copied into `apps/lab/`, and
  no asset is fetched at runtime. The same helper supplies the Pixel Manipulator's sample image.
- Code samples show the shared `pixel.run({ ... })` API with the current slider values instead of
  the old `usePixel()` hook.

## Run

From `apps/lab`, run `vp dev` and open `/experiments/pixel/`. Vite discovers the page through the
existing `experiments/**/index.html` collection; no registration is needed.

## Non-goals

- No React, no JSX, no state library, no StyleX, no router and no workspace import alias.
- No TypeDoc integration and no generated API pages: the internals copy is static and hand-written.
- No file upload in the docs page. Uploading and the eight workflow presets belong to the separate
  Pixel Manipulator experiment.
- No `maximumPixels` control; the engine keeps its 16,000,000-pixel default.
- No new dependency, no build configuration change and no change outside `apps/lab/`.
