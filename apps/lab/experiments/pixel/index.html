Pixel Docs

Documentation interactive du moteur de traitement d’image : chaque manipulation est exécutée dans un worker et illustrée sur une image source.

pixel

TypeScript-first, browser-based image manipulation pipeline. Zero dependencies. Chain built-in manipulations into reusable pipelines. Runs off the main thread via a Web Worker pool for non-blocking UI.

Why a Pipeline API?

Canvas 2D filters are limited and synchronous; direct pixel access blocks the main thread. This pipeline is composable, runs off-thread and returns one snapshot per step.

Architecture

  • run({ sourceImageData, steps }) — execute a pipeline.
  • manipulations — browse the catalog.
  • getManipulationsByAccess(type) — filter by access.
  • teardown() — release the worker pool.

Hidden internals: a worker pool (up to 4 workers), a registry and fusion scheduler, a double-buffered manager and 512-pixel tiled convolution. Three operation types: pixel, neighborhood and global.

pixel (recommended)

import { pixel } from 'pixel';

const result = await pixel.run({
  sourceImageData: source,
  steps: [
    { id: 'brightness', options: { value: 1.2 } },
    { id: 'sharpen', options: { strength: 1.5 } },
    { id: 'edge-detect' },
  ],
});

result[0];       // first snapshot
result.at(-1);   // final result

Browse available manipulations

pixel.manipulations;
pixel.getManipulationsByAccess('pixel');
pixel.getManipulationsByAccess('neighborhood');

PIPELINE /pipeline/chaining

Compose multiple manipulations into a single pipeline run

How Chaining Works

Steps run in order. Consecutive pixel operations are fused into one pass; neighborhood and global operations flush pending pixel work. Use snapshot to keep an intermediate result. 

const result = await pixel.run({
  sourceImageData: source,
  steps: [
    { id: 'brightness', options: { value: 1.2 } },
    { id: 'contrast', options: { value: 1.3 } },
    { id: 'sharpen', options: { strength: 1.5 } },
  ],
});

Execution engine

runPipeline({ source, steps, context })
  ├─ BufferManager(source)        // double-buffered pixels
  ├─ FusionScheduler()            // deferred pixel operations
  ├─ for each step
  │    ├─ snapshot    → flush / clone / store
  │    ├─ manip       → dispatchStep(...)
  │    │    ├─ resize       → computeTargetDimensions() + resizeImageData()
  │    │    ├─ pixel        → FusionScheduler.add() (deferred)
  │    │    ├─ neighborhood → flush + convolution (tiled above the budget)
  │    │    └─ global       → flush + transform
  │    └─ ...
  ├─ flush()
  └─ return { source, final, snapshots }

BufferManager

Two Uint8ClampedArray buffers are swapped by an O(1) pointer flip. snapshot() clones the current buffer; replaceWith() resets both buffers when geometry changes.

Fusion scheduler

Consecutive pixel manipulations are applied in a single traversal instead of allocating one image per step. Non-pixel operations force a flush. 

for (let i = 0; i < pixelCount; i++) {
  red, green, blue, alpha = current[i];
  for (const [definition, options] of batch) {
    [red, green, blue, alpha] = definition.function(red, green, blue, alpha, options);
  }
  other[i] = clamp([red, green, blue, alpha], 0, 255);
}

Neighborhood tiling

TILE_SIZE = 512. extractTile() copies a padded region (halo = manipulation radius) with clamped coordinates, convolution runs on the tile, then blitTile() writes only its center.

Peak memory becomes (TILE_SIZE + 2 × halo)² instead of width × height for large images.

Resize algorithm

Bilinear sampling maps each destination pixel back to the source:

sourceX = x * (sourceWidth / targetWidth);
x0 = floor(sourceX);
x1 = min(x0 + 1, sourceWidth - 1);
top = source[y0] * (1 - fx) + source[x1] * fx;
bottom = ...;
result = top * (1 - fy) + bottom * fy;
Case Behavior
maximumPixels Auto-downscale to the pixel budget.
width + height + fill Exact dimensions, stretched.
+ contain Fit inside, preserve aspect.
+ cover Fill, preserve aspect, crop.
width only / height only Other dimension proportional.

Worker architecture

pipeline-worker.ts

Stateless worker: it rebuilds the registry from the shared manifest for each message, runs the pipeline and transfers result buffers back with zero-copy postMessage.

Worker gateway

Main-thread pool with lazy creation and a FIFO queue.

Pool: up to min(hardwareConcurrency, 4) workers
Queue: FIFO
Dispatch: postMessage with Transferable buffers
